# 规模上限：当前设计的真实边界

在成熟的检索指标上继续调参已进入噪声区间（`hit@1` 0.62–0.64 之间波动）。
真正的高峰在**未验证的维度**。这份记录测量了其中最关键的一个：规模。

## 实测（595 部法规 / 24,705 索引页）

| 指标 | 数值 | 推到 10 万页 |
| --- | --- | --- |
| 冷启动建索引 | **20.8s** | ~84s |
| 进程峰值内存 | **363 MB** | ~1.5 GB |
| 每万页内存 | **147 MB** | — |
| 搜索延迟 | 中位 20ms / p95 91ms | 候选集变大，会上升 |

## 条文级索引让页数膨胀 41.5 倍

```
595 部法规 → 24,705 索引页
```

这是**有意为之的取舍**：文档级索引 `hit@1 = 0.2074`，条文级 `0.5259`（+31.8pt）。
代价是页数。

## 发现的生产阻塞

默认上限 `DEFAULT_MAX_DOCUMENTS = 50,000`：

```
595 部法规已用掉 49%
→ 约 1,200 部法规就会撞到上限
→ 之后摄入直接报错
```

**好在它失败得响亮**（`RetrievalError: BM25 index capacity reached`），
是项目"不静默降级"原则的正确实现——不会静默丢弃文档。但**触发点对一个正常规模的语料库来说太早**。

### 修复

- 默认值 50,000 → **200,000**（按实测内存推算：约 2.9 GB，支持约 4,800 部法规）
- 达到容量的 **50% 时开始告警**，让运维在还有余量时就知道内存走向
- 补 3 个测试锁定：容量耗尽必须抛错、不能在耗尽前丢弃、告警必须在撞墙前出现

## 为什么上限不该再继续调高

内存与「页数」成正比，而页数是条文级索引的必然代价。**200,000 页 = 2.9 GB 进程内存**，
再往上加就需要改变索引结构本身（例如把条文索引放到磁盘或独立服务），
那是架构决定，不是调参。

## 尝试并否决的节省内存方案

| 方案 | 结果 |
| --- | --- |
| 换 `cjk_bigram` 分词（词项更少） | `hit@1` 0.6185 → 0.5667，**效果下降** |
| 降低条文粒度 | 这正是条文级索引存在的理由，会回到 0.2074 |

**内存不能靠牺牲这个改进来省。**

## 下一步该验证的（按风险排序）

1. **合同类文档** — 数据结构与法规不同（双方义务、条款交叉引用），语料里还没有真实样本
2. **PDF 扫描件** — 依赖多模态模型，当前未验证过整条链路
3. **超大规模实跑** — 上面是推算，需要在 10 万页规模上实测冷启动与内存
4. **多轮对话** — 已验证工作正常（3 轮追问的指代消解准确），但不是这次的重点发现
