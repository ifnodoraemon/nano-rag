# 证据可见性：从 1600 字前缀到按查询词定位段落

## 问题

语料里 **595 部法规全部是单 chunk**（一部 5k–9k 字）。

证据审计读每个 context 的方式是 `text[:1600]` —— 对整部法规的 chunk 来说，
这恰好是**标题 + 制定说明 + 目录**，即 front matter。

实例：`沈阳市民用建筑供热用热管理条例` 共 5,676 字，第二十六条
「本市正常供热运行期为每年11月1日至翌年3月31日」在第 3,042 字处。

审计回答"未包含供暖起止日期"，于是：

```
审计判 sufficient=False
    → 触发纠错召回（多跑一整轮，+15s）
    → 第二轮拿到同一批文档，仍按 text[:1600] 读
    → 仍判 False
    → 拒答（或侥幸通过）
```

**270 条端到端评测中的量化**：
- 1600 字上限平均只暴露 **31%** 的句子
- **42 条拒答里 16 条**，与审计自己 `missing_terms` 匹配的那句话**就在它拿到的 context 里**，只是落在可见切片之外

## 为什么"把数字调大"不是修法

任何固定前缀都有同一个形状的 bug：答案在任意 offset，加长前缀只是把切线往后移一次。
答案在第 3,042 字，默认 1600 不够；换个文档答案在 8,000 字，给 4,000 还是不够。

## 修法

`app/agentic/evidence_view.py` 的 `EvidenceDriller`：

1. **按文档分配字符预算**（相关度加权 water-fill），而不是每个 context 平均分
2. **文档内按 `watch_terms` 定位段落**，而不是从头开始取
3. **窗口铺满全文**，保证任意 offset 的内容都有机会被看到
4. 每个 slice 都是**带 offset 的 verbatim 切片**，不发明内容
5. 能覆盖全文时置 `exhausted=True`，让审计能区分"文档里没有"和"没给我看"

### 确定性，不引入第二个模型

`watch_terms` = 用户 query + `_decompose` 产出的 subqueries，都是**模型产出的自然语言**。
driller 只做字面/词法匹配（`casefold()` substring）——零语义词表、零 embedding、零 rerank。
这与 CLAUDE.md 中 BM25 的定位一致：排序来自词法索引，不来自第二个模型。

## 配套修复（三者缺一不可）

1. **合成与审计看同一份视图** —— 否则审计判对了，合成仍可能因收到同样的"证据不足"信号而拒答
2. **`prompt_builder` 的硬指令加前置条件** —— 旧逻辑是「`evidence_sufficient=false` 就**必须**说证据不足」；
   新逻辑仅当 `evidence_complete=true`（审计确实看完了全文）才是硬指令，否则交给模型自行判断
3. **删掉"判 False 后就地重读一次"** —— 实测重读额外暴露的 term 是 **0 个**
   （首轮视图本身就是 term-driven 的，没暴露的 term 就是 contexts 里真的没有），纯亏一次 LLM 调用

## 效果（40 条端到端，基线为文档粒度修复之后）

| 指标 | 改前 | 改后 |
| --- | --- | --- |
| 拒答 | 2/40 (5%) | **0/40 (0%)** |
| 多轮触发率 | 20/40 (**50%**) | **2/40 (5%)** |
| 延迟 p95 | 24.8s | **20.2s** |
| tokens/query | 8,008 | **6,022**（↓25%） |

**18 条原本触发纠错的查询变成单轮。** 两条原本拒答的直接答出来了：

- tb-22「打工的工资标准和奖金到底谁说了算」→「开发区企业职工的工资标准…由企业自主确定 [C1]」
- tb-36「供暖一般从几月几号到几月几号」→ 答出两个城市的供热期，
  **正是原来被挡在 1600 字外的那句**

期望文档曝光率：**28% → 85%**（以 270 条旧 run 的 contexts 为输入直接测量）。

## 范围边界（不夸大）

修的是**环节 A**：选中了这篇文档，但没摘到答案所在段落。

触发率从 50% → 5% 已接近**环节 B / 真语义缺口**的天花板：
剩下 2 条是因为纠错的 follow-up query 恰好没命中检索。
**不要把 5% 当成"再优化还能降"的基线。**

## 一个开发过程的记录

作者在窗口选择逻辑上反复调参，中间有几次**把测试改成迁就实现**。
最后改用实测数据定稿——拿 270 条旧 run 的 contexts 直接量"期望文档曝光率"（28% → 85%）。

测试断言的是可验证的不变量（verbatim、offset 正确、预算不超、`exhausted` 语义准确），
不是调参结果。**这个转变值得记录：调参时指标应该来自真实数据，而不是来自你自己写的断言。**
