# 三项并行优化：实验数据汇总

## 关键结构发现（270 条 trace 实测）

| 类别 | 数量 | 占比 | e2e 中位 |
| --- | --- | --- | --- |
| 单轮查询 | 103 | 38% | 20.3s |
| 多轮查询（触发纠错召回） | 167 | **62%** | 35.6s |

纠错召回的价值：

| 类别 | 数量 | 最终回答 | 救回率 |
| --- | --- | --- | --- |
| 单轮 | 103 | 102 | 99% |
| 多轮 | 167 | 126 | **75%** |

**关掉纠错，拒答会从 42 条涨到 185 条（69%）。** 所以不能删，只能降低触发率。

`(answerable, 是否回答)` 完全一一对应，无交叉：228 True/True，42 False/False。
说明审计的 False 必然阻塞回答，纠错召回是唯一救援通道。

## 62% 的成因诊断

- 审计 `coverage_ratio`：sufficient=True 组 p50=1.00，False 组 p50=0.05、p90=0.20，完全分离
- **不是"判太严"**：False 组 90% 覆盖率不到 20%
- 159 条 insufficient 行里，**123 条（77%）**的 `missing_terms` 就在拿到的完整 context 里，
  只是在 1600 字前缀之外 → **截断是主因之一**
- 但把整份文档都给审计（`exhausted=True`）后，剩下的仍然判 False → **剩下的真缺口是 scope 错配**

## Scope 偏好：先验检查（未实跑）

| 上下文来源 | 地方性法规 | 全国/其他 |
| --- | --- | --- |
| 全部 270 条 | 317 (49%) | 329 (51%) |
| 单轮 103 条 | 99 | **143** |
| 多轮 167 条 | 218 | 186 |

单轮（审计判 True 的那些）里全国性本来占多数 → 检索**没有**系统性只返回地方变通规定。
与之前「scope 偏好 hit@1 0.5259 → 0.5259，收益为零」自洽。
风险：若答案只存在于地方变通规定（如"男的多少岁能结婚"库里只有自治州变通规定），
scope 偏好会把唯一能答的文档排下去，**触发率和拒答率同时恶化**。

## 检索召回不是瓶颈（已证伪两条路）

对 270 条 trace 交叉 `expected_doc_ids`（`answer.json`）与 `retrieval_params.discovery_hits`：

| 轮次 | n | top-12 含 expected doc |
| --- | --- | --- |
| 单轮 | 103 | **103 (100%)** |
| 多轮 | 167 | **164 (98.2%)** |
| 全部 | 270 | 267 (98.9%) |

**99% 的查询，正确文档就在 BM25 的 top-12 里。** 因此未对以下任何一项做优化：

- BM25 索引 / `top_k` / 候选集：`search_weighted` 的候选来自 query term 的 posting list
  并集（本语料约 1.7 万文档），`top_k` 只影响最后切片；实测 `fetch_k` 从 12 到 288
  耗时 0.11–0.16s，全部落在噪声内。
- `DISCOVERY_OVERFETCH_MULTIPLIER`：270 条里 version filter **丢弃 0 篇**（79% 的
  groups 为空；非空的 21% 是"每个 source_key 各建一组、组内只有 1 篇"），且 overfetch
  本身 0 成本。砍它省 0 秒，自适应它只为 0 秒收益引入语义分支。
- 查询扩展 / scope 排序：答案已在候选池里，两者都无法让它"更在"。

## 62% 的成因拆解：两个不同的丢证据环节

`(轮次 × top-12 含答案 × 深读含答案 × 是否回答)`，深读判定用 `read_doc_ids`：

| 轮次 | top-12 | 深读 | 回答 | 条数 |
| --- | --- | --- | --- | --- |
| 1 | 含 | 含 | 是 | 93 |
| 1 | 含 | 不含 | 是 | 9 |
| 1 | 含 | 不含 | 否 | 1 |
| 2 | 含 | 含 | 是 | 105 |
| 2 | 含 | 含 | **否** | 25 |
| 2 | 含 | 不含 | 是 | 21 |
| 2 | 含 | 不含 | 否 | 13 |
| 2 | **不含** | 不含 | 否 | 3 |

- 单轮：深读含答案 90.3%，回答 99.0%
- 多轮：深读含答案 77.8%，回答 75.4%

由此得到两个**不同**的丢证据环节，此前被混为一谈：

- **环节 A — 选中了，但只读了前缀。** 答案文档进了 reading plan，但摘录是
  `text[:1600]`，答案落在后面。159 条 insufficient 行里有 123 条（77%）的
  `missing_terms` 就在它拿到的完整 context 里、只是落在前缀之外 —— 这批
  `evidence_view` 能救。
- **环节 B — 根本没选中。** 12 个候选里有答案文档，reading plan 却没选它，于是答案
  连 context 都没进。

**现有 trace 无法区分 A 和 B 各自的贡献**，因为 `reading_plan` / `verification` /
`read_doc_ids` / `step_latencies` 都是覆盖写，多轮查询的第一轮数据全部丢失。
唯一解决办法是把每轮结果存成数组（`rounds: [{plan, check, read_doc_ids, ...}]`）——
这比再跑十次评测更能定位问题，也是验证任何证据可见性修复是否击中要害的唯一途径。

## 延迟构成

| 阶段 | 说明 |
| --- | --- |
| BM25 检索 | **0.02-0.19s**，不是瓶颈（曾被误报为 6.8s，实为环境噪声） |
| read_plan | 一次正常 LLM 往返（4s 量级），prompt 仅约 1.3k tokens，**不臃肿** |
| generation | 4s 量级 |
| deep_read | 0.001s |
| 纠错第二轮 | 约 15s/次，**62% 触发，是最大的一块** |

**LLM 调用次数是唯一杠杆。**

## 已完成的改动

1. **stage timing 拆分**（lead）：`agentic_discovery_seconds` 原本混合了检索+计划+深读，
   现在拆成 `discovery_search_seconds` / `read_plan_seconds` / `deep_read_seconds`。
   没有这个拆分，所有延迟归因都是猜的。
2. **expand_query 与首次 BM25 重叠**（perf-tuner）：纯调度改动，候选集完全不变。
   `_discover_with_expansion` 先 `ensure_future` 原始 query 的 BM25，再 `await
   expand_query`；展开调用抛错时 `cancel()` 掉那个 future，避免留下未 await 的
   coroutine 并把真实的模型错误盖掉。新增两个测试：一个用记录在途请求数的 searcher
   包装器 + 会 `await asyncio.sleep(0)` 的假展开客户端，断言模型调用挂起期间搜索确实
   在途；一个断言失败路径不留残骸。
3. **evidence_view 证据视图**（refusal-fixer，进行中）：按缺失词定位段落，
   修"摘录只取前缀、答案在 1600 字后丢失"。

## 测量事故记录（本项目第 4-6 次）

1. **lead**：用 `agentic_discovery_seconds > 14s` 估算纠错触发率得 24%，实际 62%。
   正确字段是 `retrieval_params.agent.retrieval_queries`。
2. **lead**：断言"BM25 检索花 6.8s 是最大瓶颈" —— 实为空载测量得 0.02s，
   6.8s 来自其他 teammate 并发跑任务造成的环境噪声。
3. **perf-tuner**：in-process 复算得到 `r1 insufficient: 0/15`，实为拿到旧签名的
   service 实例（refusal-fixer 正在改构造签名），该次测量无效。
4. **perf-tuner**：断言"plan prompt 臃肿导致 4s"，实测 body 仅 600-1450 字符、
   整包 2.7k 字符，自我修正。

**共同教训：测量工具和数据来源必须随结论一起报告，否则无法区分系统问题和工具问题。**
