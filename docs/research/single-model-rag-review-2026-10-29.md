# 单一 LLM 的 RAG 审查与后续技术路线

审查日期：2026-10-29。代码基线：`e63d405`。约束：所有语义任务复用同一个 LLM；不增加 embedding、学习型稀疏编码器、独立 reranker 或其他判别模型。

结论：现有技术路线可以继续走。下一轮最有价值的工作，是把条文命中位置可靠地交给深读与生成，再增加受预算约束的导航和多跳动作。继续堆查询改写、模型评分或扩大上下文，无法修复已经找到的证据在后续阶段丢失的问题。

本次检查了摄入、解析、条文索引、BM25、版本过滤、阅读计划、图扩展、证据视图、生成、引用检查、追踪和评测代码，并复核既有研究记录与外部一手资料。后端现有测试为 **590 passed，5 warnings**。另做了 8 组确定性复现；结果见同目录的 `.probes.py` 和 `.probes.json`。复现只使用临时语料和受控输入，不调用真实模型；它们证明具体代码行为，不代表这些问题在生产请求中的发生比例。本次没有重新运行付费端到端基准，新增技术的收益均待留出集验证。

**1. 已有能力与单模型边界**

| 能力 | 当前实现 | 审查判断 |
| --- | --- | --- |
| 词法检索 | `retrieval/bm25.py`，倒排、标题字段、中文分词、加权查询 | 保留为稳定的第一跳 |
| 条文级召回 | `wiki/article_index.py`、`WikiCompiler.write_article_pages` | 已经有；下一步应补命中位置到原文节点的映射 |
| 文档去重与粒度折叠 | 内容去重；每篇文档保留最佳匹配页 | 已经有；仍应在文档候选内部保留多个有效条文位置 |
| 查询扩展与 RRF | `agentic/query_expansion.py`，源码默认开启 | 已经有，不应再次列为新技术 |
| 假想文档与词项反馈 | `agentic/hyde.py`，源码默认关闭 | 已有实验实现；这是 BM25 适配，不是原版稠密 HyDE |
| 阅读计划与计划排序 | 同一个 `GenerationClient` 选文档、章节及顺序 | 已经有，不需要另加一个排序模型 |
| 合成问题 | `wiki/doc2query.py`，文档级最多 8 问，默认开启 | 缺答案定位、事实支撑校验和独立字段权重；提示词固定要求中文 |
| 证据摘取与纠错 | `evidence_view.py`、`service.py`，默认总检索预算为 2 轮 | 机制已有；跨阶段契约仍有缺口 |
| 图扩展 | 结构图、实体关系、PostgreSQL/artifact 邻居读取 | 实现存在，但默认 `auto` 缺触发信号 |
| 评测 | 检索、读计划、答案、拒答、引用、显著性与门禁 | 框架较完整；需要修复端到端计时、总调用成本和证据可见性口径 |

查询理解、阅读计划、审计、回答、图抽取等确实复用生成客户端。但 **“一个 provider / 同一模型家族”不等于“同一个模型”**：`configs/models.yaml:6` 与 `:13` 分别配置 generation 和 document parser；`core/config.py:356` 分别构造两者。默认 agentic parser 使用生成客户端，解析失败后 `ingestion/structured_parser.py:67` 仍可转入独立 parser 配置。

如果要求所有文件类型也只使用一个模型，应把模型身份设为唯一来源，解析和生成适配不同 API 协议时仍绑定同一后端模型及版本。模型需覆盖实际用到的文本、图片和工具能力；不支持的格式应明确报错。现有独立解析配置可以指向同一模型，但代码目前不保证这一点。索引与解析缓存指纹还应纳入实际使用的生成模型和语义提示词版本，避免换模型后混用旧的派生索引。

**2. 应先修复的实现缺口**

下面的“高”指影响答案或评测可信度，并不表示所有请求都会失败。R1—R6、R9 有附带脚本中的确定性复现；R7—R8 来自配置与调用链检查。

| 编号 | 优先程度 | 触发条件与影响 | 代码位置 |
| --- | --- | --- | --- |
| R1 | 高 | 有元数据过滤时，条文页被排除，退回只检索摘要的覆盖范围 | `app/wiki/search.py:409` |
| R2 | 高 | 深读和上下文构建先截断，证据视图无法再找回尾部；完整性标记只认识截断后的文本 | `app/agentic/discovery.py:952`、`app/retrieval/context_builder.py:206`、`app/agentic/evidence_view.py:367` |
| R3 | 高 | 审计与生成使用不同检索词重新摘取，审计认为存在的答案可能没有交给生成 | `app/agentic/service.py:704`、`:884` |
| R4 | 中高 | 纠错轮扩大 fetch，但阅读计划仍只看到前 12 个；没有已读候选排除状态 | `app/agentic/discovery.py:294`、`:658` |
| R5 | 高 | 只召回旧版本时，`include_stale=false` 仍可选中明确标记为过时的文档 | `app/agentic/discovery.py:604` |
| R6 | 中 | 默认图扩展读取 `query_route`，正常发现 trace 没有生产该字段 | `app/agentic/service.py:595`、`app/agentic/discovery.py:223` |
| R7 | 高 | 评测报告的延迟和 token 未覆盖整个问答流程，会误导技术取舍 | `app/eval/service.py:226`、`app/agentic/service.py:1006` |
| R8 | 中 | 单模型约束没有配置校验；部分默认行为与研究记录不一致 | `configs/models.yaml`、`app/agentic/discovery.py:151` |
| R9 | 高 | 引用数字和词汇重合不能证明主张成立，错误答案可同时拿满两项引用分 | `app/generation/citation_check.py:309` |

R1 的复现使用一份真实经过 WikiCompiler 编译的临时文档，目标词只出现在后部条文。无过滤时返回 `doc-policy / article`；加上完全匹配的 `doc_types=[policy]` 或有效日期过滤后都返回空。原因有两层：过滤分支限定 `kind in {topic, source}`；条文元数据自身也没有完整的父文档版本和类型信息。修复应让条文按父文档 provenance 过滤，并继续参与召回，不能只放开 kind 条件。

R2 有三个独立的预算边界。无 focus 时深读只取前 24 个 chunk；`build_contexts` 又把每个文本裁成 6000 字符；EvidenceDriller 最后只处理前 12 个 context。这些预算本身合理，但需要跨阶段保留“读了什么、遗漏了什么”。复现中 6958 字符的原始 chunk 尾部有答案，传到证据视图只剩 6000 字符、答案消失，`excerpt_exhausted` 却为 true。另一复现里，文档 A 有 24 个 chunk，随后文档 B 有答案；证据视图的 12 个名额全被 A 占用。

修复应保留完整 artifact，通过节点 ID 和原文范围按需读取；先按文档或子目标分配预算，再选段落。完整性至少区分原始文档是否读全、所选节点是否读全、节选是否读全。不能把一个完整显示的 chunk 等同于完整阅读了一篇文档。

R3 的审计 watch terms 是 `[query, *subqueries]`，生成却只用 `[query]` 重算节选。复现里审计可见位于 offset 1898 的 `17 days`，生成节选不再包含它。应该在状态中保存一份不可变的证据集合，审计、生成和引用验证共享它；PromptBuilder 也不应在审计之后无记录地再次裁剪。原文完整上下文仍可供界面展开，但不能替代“模型实际看见了什么”的记录。

R4 的受控词法排名有 100 篇文档。第一轮 fetch 为 48、第二轮为 96，但两轮阅读候选均为 `doc-001` 至 `doc-012`，新增候选为 0。更换查询仍可能改变排名，过量抓取也可能帮助版本去重，因此这不是说纠错完全无效；问题是当前 depth 参数不保证向后探索。需要记录已读节点、已拒绝候选和剩余候选，并明确区分“换查询”与“继续读后续候选”。

R5 的版本选择只比较召回池内同 source_key 的文档，没有利用 `is_latest_version=false`、`superseded_by` 去核对全局版本链。复现里只输入一个明确过时的命中，依然选中了它。应先解析用户是问当前版本、指定版本、历史时点还是版本对比，再从版本登记表选择适用版本。单纯增加 overfetch 不能保证召回一份不含旧词汇的新版本。

R6 不是缺少图模型。`_expand_graph_contexts` 的 auto 模式依赖 `retrieval_params.query_route.requires_graph`，而当前发现链没有写入该信号，正常 trace 的复现扩展次数为 0。优先让既有查询计划输出可验证的图动作，或直接沿原文引用边读取；直接全量开启 always 仍需测噪声与成本。

R7 需要先于性能实验修复。TraceSession 在发现与深读结束时就写入 `latency_seconds`；完整流程虽然另存 `step_latencies.agent_end_to_end_seconds`，EvalService 和 BenchmarkService 主要读取的仍是前一个字段。`generation_usage` 也只保存最终合成调用，漏掉查询分解、scope、扩展、阅读计划、审计和纠错。建议统一记录请求总耗时、所有调用的 usage、重试与阶段，并保存 `rounds[]`，避免只留下最后一轮审计信息。已有 ingest TokenLedger 的结构可以复用，注意并发任务的归集。

R8 除单模型配置外，还包括 scope 默认值：历史复盘说“未证实、默认关闭”，当前源码却是 `_flag("RAG_SCOPE_PREFERENCE_ENABLED", True)`。部署可能有环境覆盖，本次没有据此推断部署状态。源码正常有候选、有证据的首轮路径通常会执行分解、scope、扩展、读计划、审计、合成 **6 次逻辑模型调用**，分解与检索并行；历史上下文、重试、纠错会增加调用。优化时应该统计实际调用，而不是把“单模型”误解为“单次调用”。

R9 的英文复现原文为 `The refund deadline is 17 days. The claim limit is 99 dollars.`，错误回答为 `The refund deadline is 99 days [C1].`，即把限额中的数字挪成退款期限。当前 `citation_integrity=1.0`、`citation_precision=1.0` 且没有 issue。它们验证了标签、数字、引用及词汇重合的部分性质，不能验证实体—属性—数值—单位的绑定关系。下一步需要结构化主张和证据范围；语义支持性仍由同一模型结合原文判断，并用人工抽查校准，不能把同模型自检当作独立事实保证。

**3. 值得继续借鉴的技术**

以下均可在我们的约束内实现。表中的收益是针对当前代码缺口的工程判断，并非已测提升。

| 技术 | 在本项目中的具体做法 | 新模型 / 在线调用影响 | 建议顺序 |
| --- | --- | --- | --- |
| 命中小单元、按需展开父级与邻接证据 | 条文页绑定 artifact 节点和原文范围；阅读计划返回节点 ID；按需加载定义、表头、上下文条件 | 无新模型；精确读取可不增加调用 | 第一批 |
| Contextual BM25 | 给条文索引补文档名、章节路径、适用范围、被引用定义；歧义补充才用同一 LLM | 主要是离线加工；在线无需额外模型调用 | 第一批 |
| PageIndex 式结构导航 | 保留 BM25 找文档，在候选文档内按章节树逐层读，允许回退和继续读 | 同一个 LLM；复杂文档可能多一次或多次调用 | 第二批 |
| IRCoT / 证据驱动多跳检索 | 根据已引用的中间事实选择下一查询，管理子目标依赖和缺证据状态 | 同一个 LLM；按复杂度分配调用 | 第二批 |
| 有证据锚点的段落级 doc2query | 问题附答案原文与节点 ID；先校验锚点，再入独立搜索字段 | 离线同模型批量生成；不需要额外相关性模型 | 第二批 |
| 分字段词法检索与精确匹配 | 正文、标题、术语别名、合成问题分字段；标识符和条号提供精确定位 | 无新模型、无额外模型调用 | 与索引实验一起做 |
| 显式引用图与有界邻居扩展 | 解析“前款/附件/第 X 节”等原文关系，跨文档实体链接保留范围与来源 | 确定性链接或同模型离线抽取；读取本身无需模型 | 有跨条款需求时 |
| 结构化表格与计算工具 | 同一 LLM 选择表、列、筛选、聚合；程序执行计算并返回带行定位的证据 | 无新模型；一次计划可覆盖多个确定性操作 | 有计算需求时 |
| 自适应调用预算与结果缓存 | 合并同一输入上的分解、scope、改写；简单问题短路径；复杂问题按缺口继续读 | 目标是减少调用，效果需 A/B | 先修成本口径再做 |
| 文档树摘要与集合级 Map-Reduce | 按现有章节/目录汇总，列举或综述问题使用覆盖明确的扫描计划 | 同模型；离线摘要或有界在线汇总成本 | 集合级问题出现后 |

Contextual Retrieval 可以只借鉴词法分支：把条文放回所属文档的语境。Anthropic 的公开 49% 降低检索失败率来自 contextual embeddings 与 contextual BM25 的组合，不能写成纯 BM25 的预期收益。我们的确定性元数据前缀也只是这一思想的适配，应单独做消融。[原始说明](https://www.anthropic.com/research/contextual-retrieval)

PageIndex 最值得借鉴的是稳定的文档节点、结构导航和按需加载。我们已具备结构树和阅读计划，适合增量补足；不必替换整个发现层。其开源/托管产品和公开成绩不能自动证明一个特定部署只调用一个模型，也不能直接迁移成我们的准确率承诺。[官方仓库](https://github.com/VectifyAI/PageIndex)

IRCoT 的核心是“下一次检索取决于已经找到的事实”。当前审计已经可生成 follow-up queries，因此不是从零引入多跳；欠缺的是可核查的中间事实、依赖关系、动作选择和新证据增量。建议仅保存精简事实与引用，不存大段推理文本。例如先定位“项目归属单位”，再依据该单位检索适用制度，最后查金额限制。[IRCoT 原论文](https://aclanthology.org/2023.acl-long.557/)

Doc2Query-- 支持“过滤无依据合成问题”的方向，但原论文使用相关性模型，不能把其效果归给我们拟采用的单模型锚点校验。可让同一次离线生成返回 `{question, answer_quote, node_id}`，验证原文位置和语义可答性；锚点存在仍不保证问题被正确回答。当前固定中文的提示词也应改成由语料和目标查询语言决定。[Doc2Query-- 原论文](https://arxiv.org/abs/2301.03266)

分字段词法检索不等于引入学习型 sparse encoder。当前已有标题独立计分，但问题文本仍追加进正文。建议给原文、上下文前缀、别名、合成问题分别保留统计和权重，以留出集确定权重，不预设某个系数必然更优。规模超过进程内索引合适范围时，可测试 SQLite FTS5 等磁盘词法索引；其支持列权重，但默认分词与我们现有中文分词不等价，迁移时必须验证召回、更新一致性和容量。[SQLite FTS5 文档](https://sqlite.org/fts5.html)

显式引用关系与结构图不依赖向量。旧调研中“GraphRAG 社区检测需要 embedding”的理由需要纠正：微软公开流程用 Leiden 检测社区，文本 embedding 是后续独立阶段。这不意味着默认 GraphRAG 整套部署符合我们的约束；可先借鉴图上的引用导航，有全库综述需求时再评估社区汇总。[GraphRAG 官方流程](https://microsoft.github.io/graphrag/index/default_dataflow/)

按需加载与小工具接口也符合单模型路线：让模型调用 `search`、`read_nodes`、`follow_reference`、`query_table`，工具负责精确读取和计算。这是对既有链路的受控扩展，必须带访问范围、调用预算、已读节点和终止条件；不需要把完整知识库塞进提示词。[Anthropic 上下文工程说明](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)

**4. 建议形成的目标链路**

```text
用户问题与对话历史
  → 同一 LLM：统一查询计划（查询、实体、适用范围、时间意图、子目标）
  → 词法发现：原文 / 上下文前缀 / 别名 / 合成问题 → RRF → 适用版本
  → 同一 LLM：阅读动作，返回文档和节点 ID
  → 工具：读取完整目标节点、定义、表头及必要邻接证据
  → 不可变 EvidenceSet：来源版本、节点、原文范围、可见范围
  → 同一 LLM：证据审计与回答；有缺口则执行有界补读/补查
  → 程序：验证引用定位、原文片段、数值与单位、可复算结果
  → 回答 + 引用 + 每轮 trace + 全部模型调用用量
```

EvidenceSet 建议包含 `evidence_id`、`doc_id`、`source_hash`、`version`、`node_id`、`start/end`、`text`、`shown_to_model` 和明确的读取完整性。现有 supporting_claims 是字符串，可演进为结构化主张、证据 ID 与引用范围；兼容输出仍由 formatter 生成。

查询计划可以合并目前重复理解问题的调用。审计和草稿也可以尝试一次结构化输出，但这是待验证的成本优化：必须同时检查错误回答和错误拒答，不能只统计少了几次调用。简单问题的短路径应是明确配置与评测过的执行策略。

列表、比较、计数和全库综述需要单独表达覆盖范围。固定 top-k 很难证明“全部”“只有”“不存在”；应让计划明确待覆盖集合，以分页、结构化筛选或 Map-Reduce 执行，超预算则说明覆盖边界。长上下文也不能代替这一覆盖契约；相关信息的位置会影响模型利用证据的能力。[Lost in the Middle](https://aclanthology.org/2024.tacl-1.9/)

**5. 暂不优先引入的方案**

| 方案 | 取舍 |
| --- | --- |
| Dense embedding、ColBERT、SPLADE 等独立编码器、专用 reranker | 增加模型，超出本次硬约束 |
| 原版 late chunking | 核心依赖长上下文 embedding；可以做按需深读，但应明确是另一种机制 |
| 再加一次同 LLM 候选评分或 RankGPT | 不违反单模型，但当前已有读计划排序；既有实验尚不足以证明额外调用值得 |
| 再默认开启 HyDE、scope 或反复查询改写 | 实现已经存在；先修默认值、证据丢失与完整成本口径，再判断净收益 |
| 整套 Self-RAG | 原方案训练模型生成 reflection tokens；可借鉴按需检索、自检思想，不能当作普通提示词插件。训练一个模型并不违背约束，但当前没有必要先承担训练工程。[原论文](https://arxiv.org/abs/2310.11511) |
| 整套 CRAG | 原方案包含检索评估器；我们已有同模型审计和纠错，应补行为契约，不能把已有机制重新命名当新增能力。[原论文](https://arxiv.org/abs/2401.15884) |
| 原版 RAPTOR 的整套构建流程 | 含 embedding 与聚类；可借鉴层次摘要，以既有文档树组织，无需照搬整套方案。[原论文](https://arxiv.org/abs/2401.18059) |
| 直接接入向量免配置的托管检索服务 | 服务对外不暴露向量或模型，并不能证明内部满足“只用同一个 LLM”的要求 |

**6. 实施顺序与验收方法**

第一批处理 R1—R5 和 R7：保住条文召回、命中位置、适用版本、不可变证据，以及完整计时与成本。同步增加覆盖这些边界的集成测试；现有单元测试会关闭多个默认模型阶段，不能替代默认链路的受控集成验证。需要严格单模型部署时，同时增加模型身份配置检查。

第二批实验 Contextual BM25、节点 ID 阅读与引用展开。把它们分别消融，确认改善发生在发现、深读还是模型可见证据，而不是只让文档级 hit@1 更好看。再补基于证据的多跳动作、段落级合成问题和合并查询规划调用。

第三批由业务问题决定：有统计计算就引入表格查询工具；有跨文件关系才增加图动作；有全库综述才建集合级摘要；真实容量与并发测量显示进程内索引不合适后，再迁移词法存储。

| 需要回答的问题 | 验收指标或实验 |
| --- | --- |
| 找到正确材料了吗 | 文档和条文 recall@k 分开；带过滤、版本、跨语言的切片 |
| 找到后真正读到了吗 | 阅读节点/原文范围召回；最终 prompt 的可见证据召回 |
| 多跳是不是在推进 | 每轮新增有效证据、子目标完成率、重复读取率、预算耗尽原因 |
| 回答是否有依据 | 逐主张支持性；实体、条件、数值和单位绑定；校准后的人工抽查 |
| 该答与不该答能区分吗 | 可答题错误拒答率、不可答题错误作答率分别统计 |
| 实际成本是否更低 | 请求总调用数、重试、各阶段和总 token、真实端到端 p50/p95；摄入成本另列 |
| 能否推广到新材料 | 按文档家族/来源/版本划分留出集，避免同文件改写问法泄漏 |

留出集至少覆盖：答案位于第 25 个 chunk 或 6000 字符之后、多个文档都含大量 chunk、同一数字不同单位、同名实体不同适用范围、旧版独有词、历史时点、跨条文定义、两跳依赖、表格跨行聚合、不可答题及查询语言与文档语言不一致的情况。

既有 270 条数据多次参与调优，而且历史记录有不同阶段与裁判口径，适合保留为回归集，不能把其单次结果直接当新方案的通用收益。上下文充分性与答案正确性也应分开测量，而非只优化拒答率。[Sufficient Context 研究说明](https://research.google/blog/deeper-insights-into-retrieval-augmented-generation-the-role-of-sufficient-context/)
